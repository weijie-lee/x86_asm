# 第18章实验报告

## 1. 实验名称

平坦模型内核开启分页和调用门；用户任务扇区为空时加载器停住。

## 2. 实验目的

- 启动第 18 章现有的 MBR 和内核，记录它自己打印出的信息。
- 核对源码要求的用户任务位置：扇区 50 和扇区 100。
- 解释为什么仓库里没有用户程序时，屏幕停在调用门安装成功之后。

## 3. 实验环境

| 项目 | 值 |
| --- | --- |
| 系统 | Ubuntu，NASM 2.16.01，QEMU 8.2.2 |
| 源文件 | `c18_mbr.asm`、`c18_core.asm` |
| 磁盘布局 | 扇区 0：MBR；扇区 1：内核。扇区 50 和 100 保持为 0 |
| 实验时间 | 2026-10-24 |

## 4. 实验原理

MBR 建立基地址为 0、覆盖 4GB 的代码段和数据段，打开 A20 和保护模式，把内核从扇区 1 读到物理地址 `0x00040000`。接着建立页目录：低地址和高半地址 `0x80000000` 先映射同一块低端物理内存，避免刚打开分页时指令指针还在低地址而立刻缺页。

内核打印状态、用 `CPUID` 显示品牌、安装调用门，然后从扇区 50 和扇区 100 加载两个用户任务。程序头的第一个双字是程序长度。

## 5. 实验步骤

仓库原来没有 `run.sh`。本次按源码里的常量补上 `c18/run.sh`：

```bash
cd c18
sh run.sh
```

脚本汇编两个文件，生成 500 扇区的 `boot_img`，MBR 在扇区 0，内核在扇区 1，其余扇区为 0。MBR 为 512 字节，内核为 4147 字节。

## 6. 关键代码说明

`load_relocate_program` 用程序长度计算页数，再交给 `loop`。`loop` 先把 `ECX` 减 1，减完不为 0 才继续。

扇区 50 全是 0 时，程序长度是 0，右移 12 位后的页数仍是 0。`ECX` 从 0 减 1 变成 `0xFFFFFFFF`，循环大约要做 42 亿次。内核到不了后面的“系统核心任务正在运行”，也创建不出两个用户任务。

这个说明已经写在 `c18_core.asm` 加载扇区 50 的位置。没有改循环本身，因为空扇区不是一个合法的用户程序。

## 7. 实验结果

等待约 5 秒，屏幕停在：

```text
  Working in system core with protection and paging are all enabled.System core
is mapped to address 0x80000000.
  QEMU Virtual CPU version 2.5+
  System wide CALL-GATE mounted.
```

没有出现用户任务标记，也没有出现 `System core task running!`。

## 8. 结果分析

三段文字分别对应分页与高半映射、`CPUID`、调用门测试。它们都在加载用户任务之前，所以即使扇区 50 非法，这三句仍然可见。缺少后两句，与“页数计算得到 0，`loop` 把计数器绕回”的源码路径一致。

第 17 章的用户程序不能直接拿来充当第 18 章的任务。第 18 章加载器还会为用户地址空间分配页并改写任务的页目录，两章的任务头后半部分和内核符号表也不能仅凭文件名替换。

## 9. 问题与修正

新增 `c18/run.sh`，只做源码已经声明的 MBR 与内核布局，不伪造用户程序。内核源码增加了空扇区会导致 `loop` 空转的注释。重新汇编后的内核机器码与加注释之前相同。

## 10. 实验结论

第 18 章内核自己的初始化已经能在 QEMU 里完成：保护模式、分页、高半映射、CPU 品牌和调用门都有屏幕证据。仓库没有用户任务，加载器会在扇区 50 上长时间空转，因此这次实验到调用门安装成功为止。
