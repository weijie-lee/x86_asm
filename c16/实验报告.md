# 第16章实验报告

## 1. 实验名称

打开分页，把内核映射到 `0x80000000`，并运行一个跨多页的用户任务。

## 2. 实验目的

- 观察分页开启后的内核提示、CPU 品牌和调用门安装信息。
- 确认用户任务运行在从 0 开始的虚拟地址上，并能通过调用门打印内存。
- 解释屏幕上的十六进制数为什么只是用户程序开头的一小段。

## 3. 实验环境

| 项目 | 值 |
| --- | --- |
| 系统 | Ubuntu，NASM 2.16.01，QEMU 8.2.2 |
| 源文件 | `c16_mbr.asm`、`c16_core.asm`、`c16.asm` |
| 磁盘布局 | 扇区 0：MBR；扇区 1：内核；扇区 50：用户程序。镜像 10000 扇区 |
| 实验时间 | 2026-10-24 |

## 4. 实验原理

开启分页的瞬间，下一条指令仍在低地址。页目录同时做两份映射：`0x00000000` 和 `0x80000000` 都先指向同一块低端物理内存。跳到高半地址后，内核可以继续使用 `0x80000000` 一带的线性地址。

用户程序从虚拟地址 0 加载。`reserved times 256*500 db 0` 增加约 128000 字节，迫使加载器按 4KB 页分配多次。程序用调用门打印自己虚拟地址开头的 88 个双字，然后调用 `@TerminateProgram`。

## 5. 实验步骤

```bash
cd c16
sh run.sh
```

实测大小：MBR 512 字节，内核 4177 字节，用户程序 129166 字节。用户程序明显大于一个扇区，和保留区的设计一致。仓库里的 `c16.png` 是早先一次图形界面运行的照片；下面的文本是这次从 `0xB8000` 读出的字符。

## 6. 关键代码说明

88 次循环每次先打印两个空格，再打印 8 个十六进制字符。总输出远超过 25 行，所以屏幕只留下最后几行。这些双字按小端显示：低地址字节出现在十六进制数的右边。

可见尾部里的 `72506574 6172676F` 和后面的 `6D`，按小端拼起来是 `teProgram` 中的字符，来自符号 `@TerminateProgram`。这证明打印的是虚拟地址 0 附近的程序头和符号表，不是一段随机物理内存。

## 7. 实验结果

```text
  Working in system core,protect mode.
  QEMU Virtual CPU version 2.5+
  Paging is enabled.System core is mapped to address 0x80000000.
  System wide CALL-GATE mounted.
  Task switching...@_@
  ............User task is running with paging enabled!............
  0001F88E  0001F85B  00000010  000001F8  00000000  74530043  676E6972  ...
  ...
  00000277  616E005B  72506574  6172676F
  0000006D  ...
  Processor HALT.
```

中间多数双字为 0，是符号表里补齐的空字节。

## 8. 结果分析

内核四条状态句都出现了，随后是用户任务自己的横幅、十六进制转储和 `Processor HALT.`。顺序与“内核初始化 → 调用门 → 切换到用户任务 → 用户任务终止 → 内核停机”一致。

`0x80000000` 这一行说明内核认为分页和高半映射已经启用。用户程序不打印自己的物理地址，这也符合“用户只看见虚拟地址”的安排。

## 9. 问题与修正

本次没有改机器码。图形照片和文本转储表达的是同一次启动过程的不同记录方式；文本转储能核对具体字符。

## 10. 实验结论

分页、高半核映射和调用门可以同时工作。一个故意放大到约 126KB 的用户程序能被按页加载，并在自己的虚拟地址 0 处读出程序头和符号表。
